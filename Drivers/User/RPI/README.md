# 树莓派(RPI)通信模块

树莓派通过 USART2 与 MCU 通信：MCU 下发单字节命令，树莓派返回约定格式的应答帧。
本模块只负责「链路 + 协议解析」，不含视觉算法与任务流程逻辑。

## 文件结构

| 文件 | 职责 |
| --- | --- |
| `rpi_config.h` | 协议与配置的唯一来源：功能开关、链路参数、命令字、应答帧规格（负载长度/字段下标） |
| `rpi_port.h` | 对外接口：单次命令、标定+目标点组合接口、原始收发调试接口 |
| `rpi_port.c` | 实现：USART2 DMA 发送 + 中断接收 → 帧校验/字段解码 → 各命令 → 标定组合 |
| `tools/rpi_tools.c` | shell 调试命令组 `rpi`（`color` / `num` / `cal` / `send`） |

## 实现分层（`rpi_port.c`）

```
组合层    RPI_Cal（标定 + 输出相对当前位置的修正量）
   ↑
命令层    RPI_Detect_Color / RPI_Detect_NUM / RPI_Calibrate / RPI_SetCompleteNum / RPI_SetGridVal
   ↑
帧解析层  RPI_Frame_Payload（定长帧校验） / RPI_Frame_FindPayload（无帧尾帧头定位） / RPI_DecodeSigned
   ↑
传输层    USART2 DMA 发送 + 中断接收(逐字节) / RPI_Send / RPI_Send_And_Receive / RPI_Send_Raw
```

- 单次命令公共流程：**链路准备**（确认树莓派已停发上一条命令的重复帧 + 清空接收）→ **DMA 发送命令**
  → 等匹配格式的应答 → 补发空闲命令 `0x11`（由 `RPI_RequestFrame` 统一封装，命令事务由模块互斥锁串行化）；
  链路准备失败（树莓派仍在重复发送）时本次命令直接返回失败，由上层重试；
- 初始化（`RPI_Init`）结束时也会补发一次 `0x11`：上电/复位时树莓派可能还停在上一次命令状态；
- 雷达链路是长会话轮询（`0x1F` 逐格取，收到 `0xEF` 结束），**不**补发空闲命令；
- 雷达/完成数量应答无固定帧尾，解析时自后向前定位帧头（可容忍前导垃圾）。

### 脏数据防护（接收侧）

USART2 的（中断模式）接收一直开着，树莓派的**迟到应答、残留半帧、调试打印**如果被下一条命令当成应答，就会解析出错误的
颜色/数字/标定偏移。传输层做了四层防护（见 `rpi_port.c`）：

1. **应答门控**：只有"正在等待当前命令应答"期间收到的数据才进入解析缓冲；其余数据直接丢弃并计数
   （`RPI_GetRxStats()`，正常应基本不增长）。
2. **命令前清空接收**：每次发送命令前 `RPI_FlushRx()` 中止中断接收并重启、清事件标志与缓冲，
   并读一次 `DR` 丢掉已锁存的残留字节，保证收到的数据属于本次命令。
3. **解析容错**：应答先累积到 `RPI_RX_ACCUM`（容忍一帧被拆成多次中断交付，帧间静默 `RPI_RX_QUIET_MS` 判定结束），
   帧解析在缓冲里**扫描帧头/帧尾对齐**，命中后**从帧头偏移处拷出整帧**，因此允许前导垃圾；
   颜色帧同样兼容 `[0xEF,color,0xFE]` 旧顺序。
4. **命令/应答匹配 + 空闲停发**：树莓派收到命令字节即切换命令状态（无需先发空闲），
   但会**反复发送同一应答**（`1.py` 的最小间隔 100ms，实际周期=主循环耗时）直到收到 `0x11`；
   MCU 收到应答后补发 `0x11`，并把"等树莓派真正停发（静默判定）"推迟到**下一条命令前**（见下节），
   避免残留重复帧污染下一条命令（同格式命令时尤其重要）。等待应答时只接受**与当前命令格式一致**的帧
   （颜色=3 字节颜色帧、数字/标定=对应负载长度定长帧），其它残留/串扰帧直接丢弃并继续等待，超时才判失败。
   典型场景：`rpi send 0A`（圆环标定）后紧跟 `rpi send 0B`（颜色），以前会把圆环帧当成颜色应答，
   现在只认颜色帧格式（且 0A 的重复帧已被 `0x11` 停掉）。

### 颜色识别会话（原料区抓取用，省掉反复颜色锁定）

单次命令接口 `RPI_Detect_Color()` 每采一帧都要"下发识别命令 → 收到一帧 → 补 `0x11`"，而树莓派每次
重新识别都要先颜色锁定（约 2s），连续确认两次就是 4s+。抓取场景改用**会话接口**：

1. `RPI_ColorSessionBegin()`：到达抓取位后只下发**一次**颜色识别命令，**暂不补发 `0x11`**，
   树莓派进入命令态后按主循环（约 100ms 一帧）连续上报颜色；
2. `RPI_ColorSessionRead()`：从连续上报流里读下一帧（不重新下发命令、不补 `0x11`），
   首帧超时用 `RPI_RSP_TIMEOUT_MS`（等颜色锁定），后续帧用 `RPI_COLOR_SAMPLE_TIMEOUT_MS`（默认 1s）；
3. 连续 2 帧命中目标颜色 → 抓完当前颜色后 `RPI_ColorSessionEnd()` **补发 `0x11`** 让树莓派停止上报；
   下一次抓取到达新抓取位后再 `RPI_ColorSessionBegin()` 重新下发识别命令
   （不在物料还夹在爪里时提前识别，避免把刚抓到的颜色锁存下来导致下一颗颜色对不上）。

> 会话期间若其它 RPi 命令要用链路（`RPI_LinkPrepare`），会先自动结束会话（补 `0x11` + 等停发），
> 不会把会话的重复帧当成新命令的应答。

### 发送：DMA + 发送完成判定

`RPI_Send()` 用 `HAL_UART_Transmit_DMA()` 启动 USART2 发送，然后阻塞等待发送完成，
返回时机与原来的阻塞式 `HAL_UART_Transmit()` 一致（最后一位数据已移出），但等待期间任务让出 CPU（不再忙等）。
完成判据用 HAL 状态而不是只看事件：**`gState` 回到 `READY` 且 `TC` 置位**即本次发送完成
（TC 中断里 `UART_EndTransmit_IT` 先把 `gState` 置回 `READY` 再回调；TC 在每次 `HAL_UART_Transmit_DMA`
开始时已被清掉）。发送完成事件只用于快速唤醒 —— ISR 里的 `osEventFlagsSet` 在 CMSIS-RTOS2 中要经
定时器守护任务延迟置位，极端拥塞时可能迟到/丢失，用状态判据兜底后不会把已发出的包误判为失败。
DMA 直接读调用方缓冲，函数返回前发送已完成，所以栈上的单字节命令缓冲无需额外拷贝。
等待超时 `RPI_TX_TIMEOUT_MS`（默认 100ms）；超时/启动失败会 `HAL_UART_AbortTransmit()` 恢复句柄并返回失败，
避免 HAL 停留在 `BUSY_TX` 导致后续发送永久失败。

> 接收与发送相互独立：USART2 是全双工，发送走 DMA1_Stream6，接收是逐字节中断，树莓派持续发送
> **不会占住发送通道**，也不会让 `gState` 变成 BUSY；发送完成判定用 HAL 状态兜底并有超时，
> 不会因为接收数据多而永久卡住。真正需要防的是下面“接收中断开销与事件节流”里的间接影响。

### 接收中断开销与事件节流

USART2 接收是逐字节中断。ISR 里 `osEventFlagsSet` 在 CMSIS-RTOS2 中要经 FreeRTOS 定时器命令队列
（`configTIMER_QUEUE_LENGTH=10`、守护任务优先级 2）投递；如果树莓派异常地持续发送（脚本卡死、波特率错误、
串口噪声等），每字节都置事件位可能把该队列打满，进而挤掉其它模块的 ISR 事件（如电机用的 `UART6_TX_IDLE`），
让以 `osWaitForever` 等事件的驱动卡死 —— 表现上像是“发送卡住”。因此 RX ISR 只在**确实有任务在等**时置位，
并做节流：

- 等待应答期间：置 `UART2_RX_CPLT`（一次应答只有几个字节，不会形成风暴）；
- 停发静默判定期间：置 `UART2_RX_ACT`，最多每 `RPI_RX_EVT_THROTTLE_MS`（20ms）一次；
- 其余时间（链路空闲，或树莓派持续发送但无人等待）：只更新时间戳和丢弃计数，不置任何事件。

静默判定的真正判据是“最后一次收到字节的时间戳”，事件只用于快速唤醒，所以事件迟到/丢失不影响正确性。
`rpi stat` 的脏数据计数持续高速增长即可发现树莓派异常持续发送。

### 停发确认延迟（把静默等待挪出关键路径）

`1.py` 的应答是"进入命令态后反复发送，直到收到 `0x11`"，其中 `SEND_INTERVAL_S`（100ms）只是**最小间隔**，
实际周期 = 主循环耗时（相机采集+检测+绘制，几十~数百 ms）。原来的做法是每条命令末尾立刻轮询等待静默
（150ms 窗口，最多 1200ms），每条命令都固定付出这段等待；现在改为：

1. 命令结束立刻补发 `0x11`（DMA 同步发送），并记录"停发待确认"（即使 `0x11` 发送失败也记录，
   因为树莓派可能没收到，必须在下一条命令前重新确认）；
2. 调用方立即拿到结果返回，去做运动/等待（通常远大于静默窗口）；
3. **下一条命令前**才做停发确认：先再补发一次 `0x11`（覆盖上一次发送丢失的情况），
   再用"最后一次收到任意字节的时间戳"做静默判定——连续 `RPI_IDLE_QUIET_MS`（300ms）没有新字节
   才认为已停发，最多等 `RPI_IDLE_MAX_WAIT_MS`（1200ms），随后 `RPI_FlushRx()` 清接收；
4. 若等待超时（树莓派仍在重复发送），**本次命令直接失败**、不做发送，保留"停发待确认"，
   下一条命令前继续补发 `0x11` 并等待（自愈式重试），避免把上一条命令的重复帧当成本次应答。

命令间隔通常足够长，第 3 步几乎零等待；静默窗口 `RPI_IDLE_QUIET_MS` 默认 300ms，
明显大于 `1.py` 的最小发送间隔 100ms，也覆盖主循环较慢的情况。
静默判定用事件标志 `UART2_RX_ACT` 唤醒（收到任意字节就置位），不再 5ms 轮询。

### 时序审计（正常路径无固定等待，超时参数只用 `-D` 调，不要改默认语义）

- **正常路径**：一条命令 = 链路准备（多数瞬间返回）→ 1 字节 DMA 发送（~0.1ms）→ 等应答（树莓派检测锁定
  1~3s，这是算法时间，不是 MCU 能省的）→ 补发 `0x11`（~0.1ms）。颜色识别会话把"每帧重新锁色 ~2s"
  改成"一次锁色 + 连续取帧"（见上节），是这条链路最大的提速点，已实现。
- **不能改小的兜底**：`RPI_RSP_TIMEOUT_MS`=6000（首帧等颜色/圆环锁定，改小会在视觉正常时误判超时）、
  `RPI_IDLE_QUIET_MS`=300（树莓派主循环周期可能达数百 ms，改小会误判"已停发"，让上一条命令的重复帧
  污染下一条同格式命令的应答）、`RPI_LOCK_TIMEOUT_MS`=12000（任务与 shell 并发时的事务锁等待）。
- **可安全缩短的窗口**：颜色会话的后续帧超时 `RPI_COLOR_SAMPLE_TIMEOUT_MS`=1000（树莓派约 100ms/帧，
  只在树莓派异常时才等满）；`RPI_RX_QUIET_MS`=5（帧间静默定界，115200 下整帧 ~0.3ms）。
- 以上超时宏现在都允许构建系统 `-D` 覆盖（`rpi_config.h` 里已用 `#ifndef` 保护），现场试验时逐项改，
  并用 `rpi stat` 确认丢弃帧计数不增长（增长说明窗口偏小、重复帧/迟到帧混入）。

### 并发保护

一条命令是"清接收 → 发送 → 等应答 → 发空闲"的完整事务，`Mission` 任务与 shell 调试命令可能同时调用，
因此传输层用递归互斥锁（`RPI_Link`）串行化事务（获取超时 `RPI_LOCK_TIMEOUT_MS`，默认 12s），
雷达长会话的每次轮询同样加锁。锁创建失败只降级为无保护，不阻断模块初始化。

## 协议

命令字节（MCU → 树莓派）与应答帧（`[0xFE, 负载..., 0xEF]`；**颜色检测例外**，见下）：

| 命令 | 功能 | 应答负载 |
| --- | --- | --- |
| `0x0A` | 圆环定位-第一次（粗加工区） | `[dir_x, dir_y, abs_dx, abs_dy, dir_angle, abs_angle]` |
| `0x0B` | 颜色检测 | `[color]`，只回传一个颜色；实际脚本帧格式 `[0xFE, color, 0xEF]`（兼容旧的 `[0xEF, color, 0xFE]`） |
| `0x0C` | 圆盘定位（原料区） | `[dir_x, dir_y, abs_dx, abs_dy]` |
| `0x0D` | 圆环定位-第二次（保留，旧暂存区第二轮命令） | 同 `0x0A` |
| `0xE1` | **暂存区定位/矫正**（暂存区专用，任务里两轮暂存区都用它） | 同 `0x0A`（带朝向误差） |
| `0x0F` | 已完成数量 | `[dir_1, dir_2, abs_1, abs_2]`，无固定帧尾；**当前脚本未实现** |
| `0x10` | 圆环内数字检测 | `[num]`；**当前脚本未实现（`shuzi_start` 为 TODO），不会应答** |
| `0x11` | 空闲（让树莓派退出当前命令状态） | 无 |
| `0x1F` | 激光雷达取一格 | `[dir_x, dir_y, abs_x, abs_y]`，无固定帧尾 |
| `0xEF` | 激光雷达扫描完成（单字节通知） | 无 |

字段约定（**必须按树莓派实际脚本 1.py 解码**，与旧文档的“0=正”不同）：

- 圆盘 `0x0C`：`dir_x` / `dir_y` 均为 **1 = 正，0 = 负**；
- 圆环 `0x0A` / `0x0D` / 暂存区 `0xE1`：`dir_x` / `dir_angle` 为 **1 = 正，0 = 负**；`dir_y` 为 **0 = 正，1 = 负**；
  （脚本本身符号位不统一，MCU 侧 `RPI_DecodeSignedOneIsPos` / `RPI_DecodeSignedZeroIsPos` 分别对应；
  已知旧实现按“0=正”统一解码，导致圆盘位置误差、圆环 dx 与 yaw 误差**符号取反**，已修正）
- `abs_*` 为幅值：位移单位 mm（脚本 `min(255, ...)` 截断，最大 255），角度单位 0.1°（同样截断到 255）；
- 圆环 `abs_angle` 上报值 = 角度(°) × 10，解析时除以 `RPI_CAL_ANGLE_SCALE` 还原为度；
- 颜色值为 `RPI_Color_t` 枚举序号（1~6），0/Empty 不发送；
- 树莓派**反复发送同一帧**（`1.py` 的最小间隔 100ms，实际周期 = 主循环耗时），直到收到新命令
  （`0x11` 空闲后停止）；MCU 收到应答后补发 `0x11`，停发静默判定推迟到下一条命令前
  （见"停发确认延迟"），等待应答时只接受匹配格式的帧；
- `RPI_Cal()` 输出的是**相对当前位置的机体系修正量**：`out->pose.x / pose.y` 为位置修正(cm，
  分别含 X/Y 固定偏移)、`pose.yaw` 为角度修正(deg，圆盘标定为 0)，不再叠加当前位姿；任务层将其交给
  底盘位置模式做精确入位（见 `Applications/chassis/README.md` §4.2.1）。
- `RPI_Cal()` 额外用可选输出参数 `out_yaw_err_deg` 把视觉 yaw 误差交给任务层：任务层可选择不用它旋转
  车身，而是在抓取/放置时由机械臂基座补偿（`mission_config.h` 的 `MISSION_CAL_YAW_FIX_WITH_ARM`，
  见 `Applications/arm/README.md`）；圆盘标定(d)无角度字段，误差恒为 0。

## 功能开关（`rpi_config.h`，均可用构建系统 `-D` 覆盖）

| 宏 | 默认 | 说明 |
| --- | --- | --- |
| `RPI_COMPLETENUM_ENABLED` | 0 | 完成数量命令链路 |
| `RPI_RADAR_ENABLED` | 0 | 激光雷达链路；还需 `PLANNER_ENABLED=1` 且 `PLANNER_PLATFORM=PLATFORM_MCU` 才真正生效（`RPI_RADAR_AVAILABLE`） |
| `RPI_CAL_SIGN_X/Y/ANGLE` | 1.0 | 标定误差方向校准：脚本 dx/dy/angle 正方向与车体坐标系相反时改 `-1.0f`（默认按脚本原样） |

## shell 调试

```text
rpi color            # 读取颜色检测结果(单色)
rpi num              # 读取圆环内数字
rpi cal d            # 圆盘标定(原料区)
rpi cal r  move      # 圆环第一次标定, 并按误差移动车体
rpi cal r2           # 圆环第二次标定(保留)
rpi cal s            # 暂存区标定(专用命令 0xE1; 也可写 storage / e1)
rpi stat             # 查看接收脏数据统计(非等待应答期间丢弃的帧数/字节数)
rpi send 0B          # 手工发送原始字节, 打印 TX/RX 原始数据
rpi send 0A 00       # 多字节同理
```

> `rpi cal` 在标定前会自动把**夹爪张开到 `ARM_CAL_GRIPPER_OPEN_DEG`（默认 -110°）**
> 并**翻转相机到标定角度**（与任务流程 `Arm_Action_CalibrationReady` 的后半段一致），
> 标定结束后调用 `Arm_Action_CalibrationFinish` 收尾但**保持该翻转角、不再翻回默认角**
> （与任务流程一致；默认角只在整臂/伸展轴回零前或 `arm flip restore` 时恢复）；
> 夹爪张开失败只提示、不中断标定。`rpi send` 原始调试命令也会在收到应答后补发空闲命令（0x11），
> 避免把树莓派留在上一个命令状态而污染后续应答。
>
> 注意应答时延：树莓派要等检测“稳定”后才回帧（颜色约 2s 锁定），所以 `rpi send 0B` / `rpi cal`
> 正常要等 1~3s 才出结果；`rpi send` 等待上限 `RPI_SHELL_RX_TIMEOUT_MS`（默认 6000ms），
> 命令应答超时 `RPI_RSP_TIMEOUT_MS`（默认 6000ms），发送完成等待 `RPI_TX_TIMEOUT_MS`（100ms），
> 树莓派停发静默判定 `RPI_IDLE_QUIET_MS`（300ms，最多等 1200ms，且在下一条命令前才做，
> 所以 `rpi send` / `rpi cal` 返回时可能还没确认停发，下一条命令前会自动补上；
> 若届时树莓派仍在重复发送，该条命令直接失败并在下次调用时自动重试）。

## 扩展新命令

1. `rpi_config.h`：加命令字、应答负载长度与字段下标（有帧尾用 `RPI_FRAME_LEN`，无帧尾用 `RPI_FRAME_MIN_LEN`/`RPI_RSP_LEN_LENIENT`）；
2. `rpi_port.c` 命令层：定长帧用 `RPI_Frame_Payload` 取负载，无帧尾用 `RPI_Frame_FindPayload`，`[方向位, 幅值]` 字段用 `RPI_DecodeSignedOneIsPos`/`RPI_DecodeSignedZeroIsPos` 解码；可选功能用 `#if` 包裹；
3. `rpi_port.h`：按功能分组导出接口；
4. `rpi_tools.c`：按需加 shell 调试命令。
