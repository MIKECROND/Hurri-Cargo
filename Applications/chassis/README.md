# Chassis 底盘运动学模块

> 麦轮底盘逆运动学、运动控制与机械参数配置。
> 本模块的"旋转中心"决定原地转体时车体绕哪个点转。导航/规划使用"车体位姿点 G"，
> 由 `CHASSIS_BODY_REF_OFFSET`（G 相对 OPS 安装点的偏移）决定；**推荐 G = 车体几何中心**，
> 这样原地转体不整体平移、凸出侧扫掠最小。运动学旋转中心 C 必须等于 G
> （`CHASSIS_ROTATION_CENTER_OFFSET`），并按真实外廓配置规划器的原地旋转扫掠半径。


## 2. 坐标与符号约定

机体系（车体坐标系）：

- `+X`：车头方向（前进）；`+Y`：车体左侧；`Z` 向上；
- 俯视（从上往下看）绕 Z 轴 **逆时针为 yaw 正方向**；
- 导航/规划使用的车体位姿点 G：`G = OPS 位姿点 P + R(yaw)·(G−P)`，其中 `G−P` 由
  `CHASSIS_BODY_REF_OFFSET_X/Y` 配置；默认 0 时 G = OPS 点（旧行为）。
- 导航/规划/`nav pose`/LCD 显示的单位：位置 cm、角度 deg；`ops view` 显示的是 OPS 原始点，
  单位 mm（两者相差上述偏移，不要混用）。

逆运动学输入 `(vx, vy, w)` 描述的是 **旋转中心 C** 的运动，而不是四轮几何中心：

- `vx / vy`：C 点在机体系下的线速度（cm/s）；
- `w`：车体绕 C 点的角速度（deg/s）；
- `w != 0 且 vx = vy = 0` 时，车体严格绕 C 点原地旋转。

## 3. 逆运动学模型与旋转中心

四轮相对旋转中心 C 的坐标：

```
        +X (车头)
         ↑
  FL ●────┼────● FR        L = WHEEL_BASE_LENGTH / 2
     │    │    │           W = WHEEL_BASE_WIDTH  / 2
  ---┼----C----┼--→ +Y     C = 四轮几何中心 + (cx, cy)
     │         │           cx = CHASSIS_ROTATION_CENTER_OFFSET_X
  RL ●─────────● RR        cy = CHASSIS_ROTATION_CENTER_OFFSET_Y
```

其中 `(cx, cy)` 是旋转中心相对四轮几何中心的偏移（`chassis_config.h`）。

逆运动学（`kinematics.c`）：

| 轮子 | 角速度力臂 |
| --- | --- |
| FL | `r0 - cx - cy` |
| FR | `r0 - cx + cy` |
| RL | `r0 + cx - cy` |
| RR | `r0 + cx + cy` |

`r0 = L + W`；轮速 = `(vx ± vy ∓/± 力臂 * ω) / R`。偏移为 0 时四个力臂都等于 `r0`，
与原实现完全一致（绕四轮几何中心旋转）。

### 3.1 问题：绕轮组中心转 ≠ 绕车体几何中心转

- 麦轮逆运动学默认把旋转中心放在 **四轮几何中心**。
- 若车体几何中心与四轮几何中心不重合（车体某一侧多凸出一截，或机械臂/外壳偏向一侧），
  原地转体时旋转中心仍在轮组中心，凸出侧到旋转中心距离更大 → 扫掠半径更大 → 扫到东西。
- 对矩形车体，绕几何中心旋转时最大扫掠半径最小（= 半对角线），且前后左右对称；
  绕任何其它点都会让最大扫掠半径变大。
- 另外导航是 **位置闭环**（OPS 位姿点 + 位置环）：如果旋转中心与 OPS 位姿点不一致，
  原地转体时 OPS 点会绕实际旋转中心画圈，位置环会反向修正、和旋转指令互相拉扯，
  轨迹出现额外偏移与抖动，扫掠范围进一步变大。

因此分两步：**① 保证旋转中心 C = 导航/OPS 位姿点**（否则原地转体时 OPS 点画圈、位置环
与旋转指令互相拉扯）；**② 让 OPS 位姿点落在车体几何中心，并把 C 配置到该点**
（此时旋转扫掠半径最小、前后左右对称）。若 OPS 点无法移到几何中心，则必须按 §5 用
"OPS 点到车体最外缘的距离"配置旋转扫掠半径。

## 4. 测量与标定旋转中心

`chassis_config.h` 中两个参数（单位 cm，机体系）：

```c
#define CHASSIS_ROTATION_CENTER_OFFSET_X 0.0f // + 向前
#define CHASSIS_ROTATION_CENTER_OFFSET_Y 0.0f // + 向左
```

默认 `0 / 0` = 绕四轮几何中心旋转（旧行为）。按下面任一方法得到数值后填入、重新编译烧录。

### 4.1 方法 A：尺量法（简单，精度取决于测量）

1. 在车体底面/顶面标出 **车体几何中心**（含所有凸出结构的外接矩形中心）。
2. 量出车体几何中心到 **前后轮轴连线中点** 的纵向距离 `dx`（向车头为正）：
   - 车体几何中心在轮组中心前方 `dx` → `X = +dx`；在后方 → `X = -dx`。
3. 量出车体几何中心到 **左右轮中心连线中点** 的横向距离 `dy`（向车体左侧为正）：
   - 车体几何中心在轮组中心左侧 `dy` → `Y = +dy`；在右侧 → `Y = -dy`。
4. 凸出量的定义要分清两种情形（决定偏移是 `e/2` 还是 `e`）：
   - **单侧延长**：车体只在一侧多出 `e`（例如总宽 30+e，另一侧仍在对称基准上）→
     几何中心向凸出侧偏移 `e/2`：前凸 `e` → `X = +e/2`；左凸 `e` → `Y = +e/2`。
   - **整体横移/纵移**：车体整体相对轮组平移 `e`（一侧凸 `e`、另一侧同时缩进 `e`）→
     几何中心偏移就是 `e` 本身。

示例：车体几何中心在轮组中心 **后方 2cm、左侧 1cm** →

```c
#define CHASSIS_ROTATION_CENTER_OFFSET_X (-2.0f)
#define CHASSIS_ROTATION_CENTER_OFFSET_Y (1.0f)
```

注意：这里量的是"车体几何中心"，前提是导航/OPS 位姿点也在这个位置（见 §4.3）。

### 4.2 方法 B：OPS 两点法（推荐，直接对准 OPS 位姿点）

原理：原地旋转时，车体上任意一点都绕**实际旋转中心 A** 画圆。用 OPS 测该点（OPS 安装点 P）
转前/转后坐标，可反算出 **P 相对实际旋转中心 A 的机体系偏移 P−A**；偏移宏为 0 时 A=O，
所以结果就是 P−O。把 `P−O + (G−P)` 填成旋转中心偏移后，纯 yaw 指令就会绕导航位姿点 G 转。

**不需要精确转 180°**：位置模式 `car pos` 是开环轮位置指令，实际地面转角可能因打滑/几何
标定偏差小于或多于指令值（例如指令 180° 只转到 155°，属于正常现象，见 §4.4）。只要用
**OPS 实测的起始/结束 yaw** 代入下面的通用公式，155° 也能得到正确偏移。

步骤（**先把两个偏移宏置为默认 0/0**；场地要开阔，保证旋转过程中不碰任何东西）：

> **必须开环标定**：标定期间导航/规划器必须空闲（不要在任务流程/`planner` 原地旋转
> 过程中标定）。导航是位置闭环，会主动把 OPS 点"按住"在目标点，闭环下测量得到的偏移
> 会接近 0，标定结果无效。`car pos`/`car key` 属于开环手动指令，可用。
>
> **必须先置 0 再测**：本方法的数学结果是"被测点相对**实际旋转中心** A 的偏移 X−A"，只有
> `CHASSIS_ROTATION_CENTER_OFFSET` 为 0（A=O）时才等于 X−O。若偏移非 0 时重跑两点法
> （例如想"验证一下"），得到的是 X−C（少了当前偏移），直接抄进去会越标越偏；
> 想验证/重标请先把该宏置 0，或直接用 §4.5 的"漂移修正法"（增量式，不需要先置 0）。

1. 把车放稳。用 `ops view` 读取起始位姿 `(x0, y0, yaw0)`（OPS 位置读数单位 **mm**，
   角度 deg）。建议低速旋转以减小打滑：先 `car par 40 80 60 80`，标定完再恢复
   `car par 80 140 70 100`。
2. 执行 `car pos 0 0 180`（位置模式原地转；实际转到多少以 OPS 读数为准，**不需要是 180°**）。
3. 等车**完全停稳**（低速时需多等一会儿），`ops view` 读取结束位姿 `(x1, y1, yaw1)`。
4. 计算旋转中心相对四轮几何中心的偏移（OPS 点 = 目标旋转中心）。记
   `Δx = x1-x0`、`Δy = y1-y0`（mm），`a = cos(yaw1)-cos(yaw0)`、`b = sin(yaw1)-sin(yaw0)`，
   `k = a²+b²`（只要实际转角不是接近 0° 或 360°，k 足够大即可）：

   ```
   offset_x_mm = ( a*Δx + b*Δy) / k
   offset_y_mm = (-b*Δx + a*Δy) / k
   ```

   - 特例：若 `yaw0 ≈ 0` 且实际确实转到 180°，上式退化为 `offset = (x0-x1)/2, (y0-y1)/2`；
   - 特例：若实际正好转 180°（`yaw1-yaw0 ≈ ±180°`，任意 `yaw0`），则
     `offset_mm = (1/2)·R(-yaw0)·(p0-p1)`（`R` 为二维旋转矩阵）。

   > 上面结果的物理含义：**被测点相对实际旋转中心的偏移**。偏移宏为 0 时实际旋转中心就是
   > 四轮几何中心 O，结果即 **OPS 点相对轮组中心的偏移 P−O**。如果已经把车体参考点配置为
   > 导航位姿点（`CHASSIS_BODY_REF_OFFSET` 非 0，见 §4.3/§4.5），`CHASSIS_ROTATION_CENTER_OFFSET`
   > 应填 `P−O + (G−P)`；工具可加 `--body-ref-x-cm/--body-ref-y-cm` 自动换算，或改用
   > `nav pose`（偏移宏为 0 时输出已是 G−O）重新标定。

   换算成 cm（保留 1 位小数）填入（下面以 `offset_x_mm=-20, offset_y_mm=10` 为例）：

   ```c
   #define CHASSIS_ROTATION_CENTER_OFFSET_X (-2.0f) // = offset_x_mm / 10
   #define CHASSIS_ROTATION_CENTER_OFFSET_Y (1.0f)  // = offset_y_mm / 10
   ```

   也可以直接用工具计算（位置 mm、角度 deg，支持任意转角、任意起始 yaw）：

   ```
   py Applications/chassis/pytools/pivot_cal.py x0 y0 yaw0 x1 y1 yaw1
   ```

   示例：`py Applications/chassis/pytools/pivot_cal.py -12.5 4.0 0 8.5 3.0 155`，
   输出会给出两个偏移宏的数值；转角 <20° 时脚本会提示重测。

5. 重新编译烧录后验证（**必须用速度模式**，见下方说明）——先明确现在"该看哪个参考点"：
   - **G = P**（`CHASSIS_BODY_REF_OFFSET` 为 0，旋转中心应对准 OPS 点）：开阔处执行
     `car vel 0 0 30`（纯 yaw、速度模式），`ops view` 的 x/y 在整个旋转过程中应基本不漂
     （只允许小幅噪声/打滑）；若之后又按 §4.5 把 G 配成车体参考点，则改看 `nav pose`；
   - **G ≠ P**（已配置车体参考点，旋转中心应对准 G）：纯 yaw 时 `ops view` 会绕圈（正常，
     OPS 不在旋转中心），应看 **`nav pose` 的 x/y 基本不变、车体几何中心不整体平移**；
   - 正/反方向各转一段，位置残差应接近对称且不随时间累积；
   - 残差不为 0 时**不必重做整套两点法**：按 §4.5 的"漂移修正法"直接把修正量加到旋转中心
     偏移上，迭代 2~3 次即可收敛（这是最终验收最直接的方法）；
   - `car info` 可打印当前偏移、四轮力臂，以及"纯 yaw 180° 对应的每轮转数/脉冲"，
     便于架空空转核对脉冲当量。

> **位置模式的限制**：`car pos`（位置模式）在 `x/y/yaw` 同时非零时，等价于一个恒定机体系
> 运动（路径是圆弧），不是"先平移后旋转"；且驱动层四轮速度幅值相同，轮子目标位移不等时
> 会先后到位。因此：
> - §4.2 标定（偏移先置 0、纯 `car pos 0 0 180`）四轮脉冲幅值相等，可用于标定；
>   即使只转到 155°，按实测 yaw 套通用公式即可；
> - 偏移非零后**不要**再用 `car pos 0 0 180` 验证"是否绕 C 转"（四轮脉冲不等，
>   轨迹有瞬态偏差，容易误判），请用速度模式 `car vel 0 0 <w>` 验证。

### 4.2.1 位置模式接口（`car pos` / 标定后精确入位）

`MotionControl_SetPosition(x, y, yaw)` 是**非阻塞**的机体系相对偏移（cm / deg）位置指令：
- 返回 `false` 表示未初始化/参数非法/电机命令队列发送失败（`car pos` 会打印错误日志）；
- 运动模式固定为"相对当前实时位置"（Emm 固件 0xFD 的运动模式 2；X 固件位置命令/回读单位
  都不同，已在 motion_control.c 用编译期保护禁止，切换固件需先补齐换算）；
  命令脉冲永远相对下发瞬间的实际位置，不依赖上一次位置目标；因此**调用时应保证底盘静止**
  （不要和导航/速度命令混用）；
- 下发后用 `MotionControl_PositionArrived()` 轮询到位：按各轮电机实时位置（S_CPOS 状态轮询）
  相对下发前的位移判定——注意**位置命令单位与实时位置回读单位不同**（命令 3200 脉冲/圈、
  Emm 回读 65536/圈，相差 20.48 倍），到位判定已把目标换算到回读单位再比较；
  到达目标容差（`MOTOR_POS_ARRIVE_TOL_READ`）并保持 `MOTOR_POS_SETTLE_MS` 不动才算到位；
  读不到电机位置反馈时按 `MOTOR_POS_FALLBACK_DONE_MS` 固定时间兜底（只表示命令已下发，
  不保证实际执行/到位）；
- 速度上限取"线速度 + 旋转分量（偏摆角速度 × 旋转半径）"折算，纯原地旋转也能按设定角速度走；
  加速度沿用 `car par` 的当前值（任务层的标定精修会临时切到 `mission_config.h` 的
  `MISSION_CAL_POS_*` 专用参数，下发后立即恢复）；
- 任务流程里"视觉标定后的精确入位"已经用它代替原来的 nav 速度闭环（见 `mission_config.h`
  的 `MISSION_CAL_POS_TIMEOUT_MS`）：标定只给几 cm/几度的小修正，位置模式比速度闭环更直接。

精度提示：标定误差主要来自打滑，`car pos` 转到 150°~200° 之间都不影响公式正确性；
打滑较大时可重复 2~3 次取平均，或用正/反向各转一次取平均。

### 4.3 导航位姿点、旋转中心与车体参考点

导航/规划把"车体位姿点"当作车体位置（规划器的 30×30 模型、旋转安全半径、任务点坐标都以它
为中心）；运动学旋转中心 C 必须与它重合，否则旋转时位姿点会画圈、位置闭环与旋转指令互相拉扯。
本工程用两个偏移把"位姿点"定义清楚（都在 `chassis_config.h`）：

1. **`CHASSIS_BODY_REF_OFFSET_X/Y`**（车体参考点 G 相对 OPS 安装点 P 的偏移，G−P，机体系 cm）
   - 0/0：导航直接使用 OPS 安装点位姿（旧行为）；
   - 非 0：`nav_local.c` 把 OPS 位姿换算成车体参考点 G（`G = P + R(yaw)·(G−P)`），
     `nav_map.c` 加载预定义任务点时做同样换算，因此**任务点物理位置不变**，
     整个导航/规划栈以 G 为车体位姿点。
   - **推荐把 G 取车体几何中心**：这样原地旋转时车体中心不动、外廓扫掠最小；
     也只有在 G = 车体几何中心时，规划器的方形车体模型才是准确对中的。
2. **`CHASSIS_ROTATION_CENTER_OFFSET_X/Y`**（旋转中心 C 相对四轮几何中心 O 的偏移，C−O）
   - 必须满足 **C = G**，即：
     `CHASSIS_ROTATION_CENTER_OFFSET = (P−O) + (G−P)`
     = §4.2 按 OPS 点标定的结果 + `CHASSIS_BODY_REF_OFFSET`。

关系图（机体系，P=OPS 安装点，G=车体参考点/位姿点，O=四轮几何中心，C=旋转中心）：

```
       O ──(P−O)──▶ P ──(G−P)──▶ G = C
       └────────── CHASSIS_ROTATION_CENTER_OFFSET ──────────┘
```

- 若 OPS 就装在车体几何中心：`CHASSIS_BODY_REF_OFFSET = 0`，按 §4.2 标定
  `CHASSIS_ROTATION_CENTER_OFFSET` 即可，旋转中心即车体几何中心；
- 若 OPS 不在车体几何中心又不配置 body ref（两者都为 0）：位姿点 = OPS 点，原地旋转绕 OPS 点，
  车体几何中心会绕它画圈（看起来"车整体平移"）——见 §4.5。
- **坐标约定与 yaw 耦合（重要）**：任务点与路线临时点都按 **P 系**声明（(x,y) = OPS 安装点
  应在的位置，yaw = 车体朝向），加载时按 `G = P + R(yaw)·(G−P)` 换算。因此
  **"同一 (x,y)、不同 yaw"并不表示原地旋转**：换算后的两个目标点相差
  `(R(yaw2)−R(yaw1))·(G−P)`，转 180° 时车身会整体移动 `2|G−P|`
  （当前标定取到 7.5cm 量级时 ≈ 15cm，看起来就是"旋转在画圆"）。
  需要原地转体不要在路线表里写两段同点异向，改用 `MISSION_NAV_MODE_ROTATE` 段
  （见 `Applications/mission/utils/mission_nav.h`：位置锁当前实测导航位姿、只改 yaw）。

### 4.4 `car pos` 转不到指令角度（例如 180° 只有 155°）怎么排查

先明确：**这与 `CHASSIS_ROTATION_CENTER_OFFSET_X/Y` 无关**（偏移为 0 时逆运动学与原实现
逐位一致）；`car pos` 是开环轮位置指令，它保证的是"四个轮子各转多少圈"，不保证地面实际
转角。常见原因按概率排序：

1. **打滑/地面摩擦或被挡住（最常见）**：麦轮原地转体靠轮子与地面摩擦，速度/加速度大、
   地面滑、重心偏都会让实际转角小于指令值；如果旋转中凸出部分蹭到障碍物/线缆，轮子会
   堵转或打滑，转角同样会明显不足（先移到开阔处，或把车架起做 §4.4 第 3 条的空转测试）。
   - 判据：重复执行 2~3 次，角度是否稳定；把速度降下来再试（`car par 30 60 40 60`，
     测完恢复 `car par 80 140 70 100`）。降速后明显更接近目标 → 打滑。
   - 处理：**标定直接用实测 yaw（§4.2 通用公式）**；需要精确绝对角度时用 OPS 闭环
     （导航/规划器的原地旋转就是闭环，`car pos` 只当粗略调试）。
2. **轮组几何参数与实际不符**：`WHEEL_BASE_LENGTH/WIDTH` 填错会让"纯 yaw 180° 对应的轮子转数"
   对应的实际转角不是 180°（转角 ∝ 1/((轴距+轮距)/2)，即 r0；与 `WHEEL_RADIUS` 无关）。
   - 判据：执行 `car pos 100 0 0`（纯平移）用 `ops view` 测实际位移 `D`；再执行
     `car pos 0 0 180` 测实际转角 `A`。
     - 若 `D/100 ≈ 1` 而 `A/180 ≈ 0.86` → 轮组几何偏小：实际
       `(轴距+轮距)/2 ≈ 当前 r0 / (A/180)`（155° 时约 21.3cm，当前配置 r0=18.35cm），
       请实测轴距/轮距（轮子中心到中心的距离）后更新 `WHEEL_BASE_LENGTH/WIDTH`。
     - 若 `D/100` 与 `A/180` **同比例**偏小 → 轮半径 `WHEEL_RADIUS` 或脉冲当量
       `MOTOR_PULSES_PER_REV` 与驱动器实际设置不一致（检查 `CURRENT_FIRMWARE` 是 EMM 还是 X、
       驱动细分设置；X 固件位置单位是 0.1°，与脉冲单位不同）。
       注意：改 `WHEEL_RADIUS` 会同时按比例改变**开环平移距离和开环转角**，改完后应重新用
       `car pos 100 0 0` + `ops view` 复测 `D/100`（理想值 1.0，即 `D/100 = R实际/R配置`）；
       它不影响旋转中心偏移标定（§4.2 用 OPS 实测位姿，与 R 无关）。
3. **脉冲当量/固件单位不一致（架空空转可判定）**：把车架起（轮子离地），在轮胎上做标记，
   执行 `car pos 0 0 180`，看每个轮子转数是否等于 `car info` 打印的"纯 yaw 180° 每轮期望
   转数/脉冲"（当前配置 WHEEL_RADIUS=3.65 时约 **2.51 圈**；R 改过后这个圈数会变，以
   `car info` 为准，README 不写死）。
   - 空转圈数正确、地面角度不足 → 打滑（回到第 1 条）；
   - 空转圈数也不对 → 脉冲当量/固件单位/细分配置问题（第 2 条后半），先核对驱动器设置，
     不要用 `car pos` 的角度作为标定基准。
4. **读数/角度本身**：确认用 `yaw1 - yaw0`（角度差）而不是绝对 yaw；确认转前转后都等
   停稳再读；OPS 丢帧/清零会导致读数跳变。

> 结论：**标定旋转中心不需要 `car pos` 精确转到 180°，也不需要先修好这个角度误差**——
> 按 §4.2 用实测 `(x0,y0,yaw0)`、`(x1,y1,yaw1)` 代入通用公式即可；`car pos` 的角度误差只在
> 你把它当"绝对角度指令"用时才需要按上面排查。

### 4.5 原地旋转时车体整体平移（绕的不是车体几何中心）

**现象**：按 §4.2 标定好旋转中心后，用 `car key` / `car vel` 原地转 180°，车体明显往前（或
后/左/右）移了一点，不是"原地自转"。

**原因**：§4.2 标定得到的旋转中心是 **OPS 位姿点 P**；如果 OPS 安装点不在车体几何中心 G，
那么旋转时 P 点固定不动、车体几何中心绕 P 画圈。转 180° 时车体中心相对起点位移约
`2×|G−P|`（G 在 P 后方时表现为"转完往前走了"）。这不是打滑，也不是偏移算错。

**先判别**（纯 yaw、速度模式 `car vel 0 0 30` / `car key`，导航空闲；同时看两个命令）：

| 现象（转 180°） | 结论 |
| --- | --- |
| `nav pose` 的 x/y 基本不变（<1cm），**车体几何中心也不动** | 配置正确。此时 `ops view` 会画圈是正常的（OPS 不在旋转中心） |
| `nav pose` 的 x/y 画圈/漂移 | 实际旋转中心 ≠ 导航位姿点 → 旋转中心偏移不一致。先用本节「漂移修正法」加修正量；修正量 >5cm 时再复查 §4.2 流程与 G−P |
| `nav pose` 不动，但**车体几何中心**仍画圈/整体平移 | 旋转中心已对上导航位姿点，但该位姿点不是车体几何中心 → `G−P` 量错（符号/参照物），按下面 1~3 重新量 |
| `ops view` 不动、`nav pose` 画圈 | 旋转中心仍对准 OPS 点（漏加了 G−P）→ `CHASSIS_ROTATION_CENTER_OFFSET` 加上 `CHASSIS_BODY_REF_OFFSET`，或直接用漂移修正法 |
| 角度不到位、伴随打滑声 | 按 §4.4 排查打滑/几何参数 |

**漂移修正法（推荐：最终验收 / 两点法残差修正，不需要先把偏移置 0）**

原理：纯 yaw 时导航位姿点 G 与实际旋转中心 A 不重合，`nav pose` 必然漂移
`G1−G0 = (R(yaw1)−R(yaw0))·(G0−A)`；反解出的机体系偏移就是旋转中心要补的修正量：

```
e_body = R(-yaw0) · (R(yaw1) - R(yaw0))^{-1} · (G1 - G0)      # 180° 时简化为 -0.5·R(-yaw0)·ΔG
CHASSIS_ROTATION_CENTER_OFFSET += e_body
```

步骤（开环、开阔场地；导航/规划器空闲）：

1. `car vel 0 0 30` 开环纯 yaw 旋转，看 `ops view` 的 yaw 转过约 180° 后 `car vel 0 0 0` 停车，
   等 1s 停稳；
2. 记录转前/转后 **`nav pose`** 的 `(x0,y0,yaw0)`、`(x1,y1,yaw1)`（`nav pose` 位置单位是
   **cm**，不是 `ops view` 的 mm）；
3. `py Applications/chassis/pytools/pivot_cal.py --drift --rot-x-cm <当前X> --rot-y-cm <当前Y> x0 y0 yaw0 x1 y1 yaw1`
   → 输出修正量和新宏值，填入后重烧；
4. 重复 1~3 直到 180° 时 `nav pose` 的 x/y 变化 < 1~2cm（一般 1~2 次收敛）。
   注意这是**增量**修正，可与 §4.2 的绝对标定叠加使用；不要在导航闭环运行时测
   （闭环会把位姿点按住，测到接近 0，无效）。

**处理（G−P 的基础配置，软件方案，任务点坐标不用改）**：

1. 量出 **车体参考点（建议车体几何中心）相对 OPS 安装点的偏移 `G−P`**（cm，机体系
   +X 前、+Y 左）。例：OPS 装在车体几何中心**前方 2cm、左侧 1cm** → `G−P = (-2.0, -1.0)`。
   注意是"OPS 在车体几何中心的前/左方 → G−P 取负"，符号别反；车体几何中心按
   **含所有凸出的外接矩形中心**取，并建议用铅垂线在车体上标出实际投影点再量。
2. 在 `chassis_config.h` 设置：
   ```c
   #define CHASSIS_BODY_REF_OFFSET_X (-2.0f)
   #define CHASSIS_BODY_REF_OFFSET_Y (-1.0f)
   ```
3. 旋转中心改为 **G−O**：
   `CHASSIS_ROTATION_CENTER_OFFSET = (§4.2 标定值 P−O) + (G−P)`。
   或把 `CHASSIS_ROTATION_CENTER_OFFSET` 先置 0，烧录后用 **`nav pose`**（偏移置 0 时输出
   即 G，两点法结果直接是 G−O）重新做 §4.2 两点法。
   注意：`pivot_cal.py` 如果输入取自 `ops view`（P），用
   `--body-ref-x-cm/--body-ref-y-cm` 传入 G−P 会自动换算；**两个分支不要同时用**
   （用 nav pose 又加 --body-ref 就会把 G−P 加两次，误差 `|G−P|`，180° 位移 `2|G−P|`）。
   最后都建议用上面的"漂移修正法"收尾验收。
4. 烧录后验证（`car key` 原地 ±180°）：
   - 车体几何中心基本不动（不再整体平移）；
   - `nav pose` 的 x/y 基本不变（<1cm，允许打滑）；
   - `ops view` 的 x/y 会画圈——正常，因为 OPS 不在旋转中心；
   - 车体四角扫掠轨迹对称；规划器扫掠半径按"G 到车体外缘最大距离"配置（§5）。
   - 注意：OPS 清零后 `nav pose` 不再显示 (0,0)，而显示 `G−P` 偏移（车体参考点在 OPS
     零点坐标系下的位置），这是正常的；`ops view` 仍显示 OPS 点 (0,0)。

> 机械替代方案：把 OPS 传感器/标记移到车体几何中心（G−P=0），再重新做 OPS 零点与 §4.2
> 标定——注意 OPS 零点位置会变，所有任务点需要重新复测（软件方案则不需要）。

## 5. 与 Planner 的配合

Planner 的原地旋转安全判定使用"旋转扫掠半径 + 2cm"，见
`Applications/Planner/planner_config.h`：

```c
#define PLANNER_ROTATION_SWEEP_RADIUS_CM PLANNER_BODY_HALF_DIAGONAL_CM // 默认 21.22cm
```

- 默认值 21.22cm 对应"30×30 对称方形、旋转中心在几何中心"。
- 车体不对称/有凸出时，按 **旋转中心/车体位姿点 G 到车体最外缘的最大距离** 实测填写。
  车体（外接矩形 a×b，几何中心 B）与旋转中心 C=G 都在同一机体系时：

  ```
  R_sweep = hypot(a/2 + |bx - cx|, b/2 + |by - cy|)
  ```

  当 C = B（绕几何中心旋转）时退化为半对角线 `hypot(a/2, b/2)`；
  例：车体（含凸出）长 34cm、宽 30cm、旋转中心在几何中心 → `hypot(17,15) ≈ 22.67cm`。
  推荐按 §4.3/§4.5 把车体参考点 G 配到车体几何中心，此时这一项就是车身半对角线。
- 该半径只影响原地旋转安全判定/执行期监测；**平移碰撞模型仍是 30×30 方形**
  （`PLANNER_CAR_SIDE_CM`）。若车体实际外廓明显大于 30×30（尤其凸出方向需要平移通过窄道），
  需同步评估 `PLANNER_CAR_SIDE_CM` 或调整任务点位，详见 `Applications/Planner/README.md`。

## 6. 验证清单

1. 编译烧录后执行 `car info`：**先核对两个偏移是否"成对"**——要么都为 0（旧行为），要么
   `CHASSIS_ROTATION_CENTER_OFFSET == (P−O) + CHASSIS_BODY_REF_OFFSET`（C=G）。只配了
   `CHASSIS_BODY_REF_OFFSET` 而 `CHASSIS_ROTATION_CENTER_OFFSET` 还是 0（或反之）时 C≠G，
   纯转 180° 时 `nav pose` 会漂 `2|C−G|`（本车若 BODY_REF≈7.5cm，错位 8.4cm → 漂 16.7cm；
   而"全 0"只漂 1.9cm，这正是"填了校准反而更差"的典型形态）。同时确认四轮力臂，
   以及"纯 yaw 180° 每轮期望转数/脉冲"符合预期（偏移为 0 时四轮力臂相等）；
   启动日志 `Planner: map ready ... rotSweep=... rotClear=...` 可核对规划器生效的旋转半径。
2. 开阔处用 **速度模式**（`car vel 0 0 30`）或 `car key` 原地正/反旋转，同时观察：
   - **`nav pose`** 的 x/y：配置正确时应基本不变（<1cm，允许打滑）；若画圈 → §4.3/§4.5；
   - **`ops view`**：若 `CHASSIS_BODY_REF_OFFSET` 非 0，OPS 点会绕车体参考点画圈（正常）；
     若其为 0，OPS 点应基本不动；
   - 地面上车体四个角的扫掠轨迹应基本对称（前后/左右对称）；
   - 凸出侧扫掠范围应明显小于修改前（原偏移量越大改善越明显）。
   - 注意：偏移非零后不能用 `car pos 0 0 180` 做此项验证（四轮脉冲不等、有瞬态偏差）。
3. 连续换向/窄通道任务：观察规划器日志 `rotate@wpN ... clear=...` 与
   `Planner: rotation unsafe ...` 是否仍在安全范围；确认没有出现"旋转过程中位置环反向拉扯"。
4. 旧行为回归：车体参考点偏移与旋转中心偏移都为 0 时，运动学/导航与修改前逐项一致
   （运动学有主机端数值验证）。
5. `car pos` 角度与指令值不符（如 180° 只有 155°）时，按 §4.4 排查；这不影响 §4.2 的
   旋转中心标定（用实测 yaw 代入通用公式即可）。
6. 原地旋转时车体整体平移 → 按 §4.5 先判别是"绕 OPS 点转"还是"偏移标错"，再按对应步骤处理。

## 7. 已知限制

- **导航位姿点的含义**由 `CHASSIS_BODY_REF_OFFSET` 决定：非 0 时 `nav pose`、规划器日志、
  LCD/串口显示的坐标都是"车体参考点"坐标，而 `ops view` 仍显示 OPS 安装点坐标；两者相差
  一个随 yaw 旋转的偏移，不要混用。
- **任务点/路线临时点是 P 系声明（yaw 参与换算）**：同一声明 `(x,y)` 配不同 yaw 时，换算后
  的目标点相差 `(R(yaw2)−R(yaw1))·(G−P)`，"同点异向"不是原地旋转；路线表里需要原地转体请用
  `MISSION_NAV_MODE_ROTATE`（位置锁当前实测导航位姿、只改 yaw），不要写两段同点异向。
- **大偏置下的旋转精度**：G−P 取到 7.5cm 量级时，四轮相对旋转中心的力臂会相差数倍
  （`car info` 可看到，例如 29.6 / 14.7 / 22.0 / 7.1cm）。力臂小的一侧轮速极低、力臂大的
  一侧轮速很高，麦轮打滑会明显偏离理想旋转中心；§4.2 低速标定出来的支点在
  `target_angular_speed=220deg/s` 的高速任务旋转下不一定成立。旋转仍不稳时按顺序处理：
  ① 用 §4.5 漂移修正法在**任务用转速**附近复测修正；② 降低 `target_angular_speed`；
  ③ 尽量把 OPS 安装点移到车体几何中心（G−P≈0），从根上减小力臂差。
- 旋转中心/参考点偏移只解决"原地旋转支点"问题；车体凸出对 **平移** 的净空影响由 Planner 的
  方形模型承担，需按实际外廓评估（见 §5）。
- 麦轮横移/旋转存在打滑，标定残差与地面摩擦有关；标定后若更换轮子/车体结构需重标。
- **速度模式的加速度参数单位**：`MotionControl_SetMotionParams()` 的 `acc/dec` 是物理量 `cm/s²`，
  下发到电机时按固件换算：X 固件是 `RPM/s`；Emm 固件是 **0-255 档位**（手册公式：每
  `(256-档位)×50us` 加速 1RPM，即 `RPM/s = 20000/(256-档位)`，反解 `档位 = 256 - 20000/RPM_s`）。
  不要把 `RPM/s` 直接强转当档位下发（Emm 只取低 8 位会截断成错误档位，例如导航曾把加速度下发成
  0 档≈30cm/s²，速度环跟不动导航指令 → 位置过冲、平移时"一前一后甩着走"）。
- 位置模式（`car pos`）：轮子脉冲严格线性叠加，但 `x/y/yaw_offset` 同时非零时对应的是
  一个恒定机体系运动（圆弧路径/常 twist），不是"先平移后旋转"的终位；且驱动层四轮速度
  幅值相同，目标位移不等时会先后到位、产生瞬态偏差。纯 yaw（x=y=0）才严格绕 C 定轴旋转。
  导航与规划都只用速度模式，不受此影响；位置模式仅用于手动调试/标定。
- `car pos` 是开环轮位置指令，实际地面转角/位移可能因打滑或机械参数标定偏差而与指令值
  不符（例如指令转 180° 实际 155°，见 §4.4）；需要精确绝对角度时用 OPS 闭环（导航/规划器
  的原地旋转），不要依赖 `car pos` 的开环角度。

## 8. 电机命令链：时延/排队根因与观测（2026-11 修复）

> 本节说明"导航算出的轮速指令从计算到电机执行"这条链路的时延问题、修复方案、带宽预算与
> 现场验证方法。代码位置：`Applications/chassis/motion/motion_control.c`、
> `Drivers/User/STEP/zdt_v5_port.c`、`Drivers/User/STEP/step_port_dlc.c`。

### 8.1 修复前的问题（静态量化）

USART6 @921600bps，8N1 ⇒ **10.85us/字节**。Emm 固件当前配置（`MOTOR_MULTI_CMD=1`）帧长：

| 帧 | 字节数 | 线速耗时 |
| --- | --- | --- |
| 多机速度命令 0xAA（4 轮打包） | 37 | ≈403us |
| 同步触发 0xFF66 | 4 | ≈43us |
| 状态轮询（单参数读） | 3 | ≈33us |
| 多机位置命令 `car pos` | 57 | ≈619us |

旧实现：**所有命令**（导航运动 setpoint / 状态轮询 / 机械臂 / 停止）共用一条深度 64 的
`MotorCmdsHandle` FIFO，且 `Motor_Ctrl_Task` 每处理一条就 `osDelay(2)`（实际 1.5~2.0ms 一条）：

- 服务率 ≈ 515~650 条/s；
- 需求：导航 5ms 周期 2 条（0xAA + 同步）= **400 条/s**；状态轮询 7 个总线电机 ×2 条/50ms =
  **280 条/s**；机械臂偶发命令 ⇒ 约 680 条/s；
- 按每条 1.5~1.9ms 折算，**每秒需要 1.12~1.29s 的服务时间（112%~129%）⇒ 必然积压**；
- 队列 64 深度在约 0.4s 内填满，之后运动指令的稳态排队时延 ≈ 64 × 1.5~1.9ms ≈
  **98~122ms**（与 `docs/nav-freq-domain-feasibility.md` 的 0.1s 级评估一致）；
- 队列满时 `Motor_Send_Cmd()` 阻塞（100ms 超时）也会落在 Nav_Task 的调用路径上，
  把 5ms 控制周期拉长到 8~9ms 甚至更久，并让"停止命令"排在队尾 100ms 级才能下发。

后果：电机执行的是 0.1s 之前算出来的速度，闭环等效为**约 100ms 纯延迟**——这正是导航
"过冲/画龙/到位后还在动"的主要根因，单纯调 PID 无解。

### 8.2 修复后的链路

| 通道 | 内容 | 语义 | 等待上限 |
| --- | --- | --- | --- |
| 紧急通道 `Motor_Send_Cmd_Urgent()` | 停止广播、使能/失能 | 环形 4 深、非阻塞、满时丢最旧 | 一帧发送 + 一个间隙（<2ms） |
| 运动邮箱 `Motor_Send_Motion_Setpoint()` | 多机打包速度 + 同步触发 | **最新值覆盖**单槽、非阻塞、旧值丢弃 | setpoint → 上线 ≤2.5ms |
| 普通队列 `Motor_Send_Cmd()` | 状态轮询、机械臂、工具命令 | 保持原 FIFO + 100ms 阻塞语义 | 正常 <10ms |

`Motor_Ctrl_Task` **每发一帧前都会重新检查一遍高优先级通道**（紧急 → 运动邮箱 → 普通队列），
因此状态轮询/机械臂的突发不会把运动或停止命令堵在后面。发送间隙由无条件 `osDelay(2)` 改为
`MOTOR_CMD_GAP_MS`（默认 1ms）。

运动 setpoint 还做了"三级限频"（`CHASSIS_MOTION_SETPOINT_*`，见 `chassis_config.h`）：
Emm 速度模式是绝对值指令，电机收到后保持速度，重复下发完全多余（心跳由状态轮询维持）：

| 指令变化 | 行为 | 实际发送率 |
| --- | --- | --- |
| 大幅阶跃（>5cm/s 或 >10deg/s） | 立即投递 | 立即 |
| 常规变化（>0.3cm/s 或 >0.5deg/s） | 最快每 10ms 一次 | ≤100Hz |
| 几乎没变 | 最多每 20ms 刷新一次 | 稳态 50Hz |

阈值造成的最大速度误差就是阈值本身（0.3cm/s / 0.5deg/s），20ms 内折算位置误差 ≤0.006cm，
远小于到位判定阈值；缓慢漂移由保持刷新补上。`car vel` 等手动命令会强制下发（不受限频影响）。

状态轮询也降了载：底盘轮子（ID 1~4）不做回零，不再轮询回零状态标志（S_OFLAG），只轮询实时
位置（S_CPOS）；机械臂电机（ID 5~7）仍两个都轮询（回零/到位判定依赖）。状态轮询帧数
280→200 帧/s（-28%），**每电机更新周期仍为 50ms**（机械臂 `ARM_SETTLE_STABLE_MS=100` 依赖它，
未改动）。

### 8.3 带宽/时延预算（修复后）

| 场景 | 运动 setpoint | 状态轮询 | 电机控制任务占用（平均/最坏） | 总线线速占用 |
| --- | --- | --- | --- | --- |
| 稳态巡航 | 50Hz | 200 帧/s | ≈18% / 33% | <3% |
| 加减速/接近目标 | ≤100Hz | 200 帧/s | ≈25% / 45% | <6% |

（"占用"按每帧"线速耗时 + 1ms 帧间隔（平均 0.5ms）"估算，含机械臂偶发命令余量；
最坏情况取所有间隙都恰为 1ms。修复前同口径为 112%~129% ⇒ 积压。）

端到端时延（Nav 计算 → 电机收到命令）：

- 运动 setpoint：投递→控制任务取到 ≤1ms + 多机帧 403us + 同步间隔 1ms + 同步帧 43us
  ⇒ **典型 1.5ms，上限 ≈2.5ms**（旧实现 100ms 级）；
- 停止命令：投递→上线 **≤1.1ms**（旧实现排在队尾，100ms 级且可能被丢）。

### 8.4 观测命令（默认零周期日志）

```
car bus        # 底盘 setpoint 限频统计 + 电机总线命令链统计
car bus r      # 清零统计
step bus       # 只看电机总线命令链统计（不经过 chassis 层）
step bus r     # 清零
step bus q     # 一行快速摘要（可在运动过程中反复敲）
```

`step bus` 关键字段与判读：

| 字段 | 含义 | 正常值 |
| --- | --- | --- |
| `motion rate` | 近 1s 实际发送的 setpoint 数 | 稳态 ≈50Hz、动态 ≈100Hz（说明限频生效） |
| `motion drop` | 旧 setpoint 被覆盖丢弃的比例 | <5%（接近 0；高说明发送能力不足） |
| `motion wait last/avg/max` | 投递→开始发送的等待(ms) | max <5ms（修复前等效 ≈100ms） |
| `slow` | 等待 >20ms 的次数 | 长期 0 |
| `urgent latency_max` | 停止/使能命令等待(ms) | <2ms |
| `queue peak` / `put_timeout` | 普通队列峰值 / 投递超时次数 | ≤2 / 长期 0 |
| `tx frames rate`、`tx max` | 总线帧率 / 单帧发送耗时(us) | 多机帧 ≈403us、轮询帧 ≈33us |
| `poll_frames` | 状态轮询帧数（累计） | 约 200/s |

### 8.5 上车验证步骤

1. **静态基线**：上电后（无运动）`car bus`，确认 `motion drop=0`、`queue peak<=2`、
   `queue put_timeout=0`；`step bus r` 清零。
2. **原地转**：开阔处 `car vel 0 0 30`，转 2~3 秒后 `car bus`：
   `motion rate` 应约 50Hz、`wait max` <5ms、`drop` ≈0；再 `car vel 0 0 0` 停车，
   确认 `urgent sent` 增加且 `latency_max` <2ms。
3. **直线加减速**：导航一段 >1m 的直线（Planner 或 `nav` 单段），跑完立刻 `car bus`：
   动态段 `motion rate` 可升到约 100Hz，`wait max` 仍应 <5ms、`drop` <5%。
4. **到位停车**：观察是否还有"导航已到位但轮子还在转"；`car bus` 的 `urgent latency_max`
   和 Nav 日志的 STOPPING 300ms 补偿是否还需要（修复后停止通常在 1~2ms 内上线）。
5. **机械臂/位置模式回归**：`step tool zero/home`、`car pos`（标定精修）各跑一次：
   确认位置回读（`step view` 不可用时可看 `car bus` 的 `poll_frames` 增长、或 `nav pose`
   正常）与到位判定时间与修复前一致；`queue peak` 不应因机械臂命令超过 3~4。
6. **A/B 对照**（台架/实车各一次）：把 `MOTOR_CMD_LEGACY_CHAIN` 置 1 重新编译（复现旧链路：
   全部走 FIFO + `osDelay(2)`），重复步骤 2~3，对比 `car bus` 的 `motion rate/wait max/drop`
   与 Nav 周期抖动；再切回 0 确认改善。
7. **间隙参数调优（可选，架起车轮做）**：确认 `MOTOR_CMD_GAP_MS`/`MOTOR_MOTION_SYNC_GAP_MS`
   能否从 1ms 降到 0（可省约 1~2ms/周期）：
   - 前置条件：连续状态轮询 + 连续速度指令下，`step bus` 的 `tx_timeout=0`、电机在线检测不
     闪断、位置回读连续无跳变、无"Motor N Response Code Unknown"/粘包告警；
   - 步骤：先把 `MOTOR_CMD_GAP_MS` 设 0（同步间隙保持 1ms）跑一轮；再设同步间隙 0 跑一轮；
     任一步出现丢命令/状态跳变/告警，立即恢复 1ms；
   - 同步触发帧与多机帧之间**不建议**为 0（驱动器需要时间缓存子命令，否则偶发某轮不同步）。
   若 Emm 固件对帧间隔更敏感，宁可把两个间隙调回 2ms（带宽占用翻倍但稳态仍 <70%），
   或用 `CHASSIS_MOTION_SETPOINT_MIN_INTERVAL_MS=20` 把动态发送率再降到 50Hz。

### 8.6 接口语义（供 nav/mission 参考）

- `MotionControl_SetVelocity(x,y,yaw)`：**永不阻塞**（最多一次 ~2us 临界区拷贝），Nav 5ms
  周期不会被它拉长；限频可能跳过"几乎没变"的指令（见 §8.2）。
- `MotionControl_Stop()`：**永不阻塞**，写紧急通道 + 作废待发 setpoint；停止之后不会再执行
  更早的速度指令；保留驱动未初始化时的队列入队兜底。
- `MotionControl_SetPosition(...)`：位置命令仍走普通队列（一次性命令，不参与覆盖丢弃）；
  下发前会作废待发速度 setpoint，并要求底盘静止时调用。
- `Motor_Send_Motion_Setpoint()`：只在任务上下文调用（内部临界区，不可在中断里用）；
  非阻塞；丢弃"未发出的旧值"。
- 驱动未初始化（`Motor_Init` 失败）时上述接口返回 false/无动作，与旧行为一致。
